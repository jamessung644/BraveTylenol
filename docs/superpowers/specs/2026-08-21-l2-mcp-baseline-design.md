# BraveTylenol L2 + MCP Baseline Design

Date: 2026-08-21

## Objective

Build a submission-ready, containerized multi-turn conversation driver for the Conquer Health hackathon. The default path uses Lunit L2 in the recommended two-stage generation/retrieval pattern with the provided medical MCP server. A passthrough mode remains available for an L2-only ablation.

The service must expose an OpenAI-compatible API on `0.0.0.0:8000`, build within five minutes, process concurrent evaluator requests, and ensure that the final user-facing answer is generated by L2.

## Scope

### Included

- `GET /v1/models`
- `POST /v1/chat/completions`
- Non-streaming OpenAI-compatible requests and responses
- Full multi-turn message preservation
- L2 generation with the single `retrieve_relevant_content` tool
- L2 retrieval with dynamically discovered MCP tools and `finalize_retrieval`
- A maximum retrieval tool-call budget
- Evidence selection, normalization, deduplication, and size limits
- MCP failure fallback to direct L2 generation
- `rag` and `passthrough` harness modes
- Async request handling, tests, and Docker packaging

### Excluded from the baseline

- Frontend or user accounts
- Model training or fine-tuning
- Streaming responses
- A separate safety model or answer-rewriting model
- Persistent conversation storage
- Cross-request retrieval caching
- HealthBench prompt-specific rules or hard-coded answers

## Runtime Configuration

Configuration is read from environment variables through a validated settings object.

| Variable | Default | Purpose |
|---|---|---|
| `LUNIT_FM_API_KEY` | none | Bearer token shared by L2 and MCP endpoints |
| `LUNIT_FM_API_URL` | `https://model.hackathon.lunit.io` | L2 OpenAI-compatible base URL |
| `LUNIT_FM_MODEL` | `Lunit/L2-preview` | Upstream L2 model name |
| `LUNIT_MCP_URL` | `https://mcp.hackathon.lunit.io/mcp` | Streamable HTTP MCP endpoint |
| `HARNESS_MODE` | `rag` | `rag` or `passthrough` |
| `MAX_TOOL_CALLS` | `4` | Maximum MCP calls in one retrieval run |
| `UPSTREAM_TIMEOUT_SECONDS` | `150` | L2 and MCP request timeout below the evaluator's 180-second limit |
| `MAX_TOOL_RESULT_CHARS` | `12000` | Per-tool serialized result limit |
| `MAX_EVIDENCE_CHARS` | `32000` | Total evidence passed to generation |

Secrets are never logged, returned by an endpoint, copied into the Docker image, or committed to Git.

## API Contract

### `GET /v1/models`

Returns one evaluator-facing model:

```json
{
  "object": "list",
  "data": [
    {
      "id": "team-chatbot",
      "object": "model",
      "owned_by": "brave-tylenol"
    }
  ]
}
```

This endpoint does not require the upstream API key, which allows container readiness checks before inference.

### `POST /v1/chat/completions`

Accepted baseline fields:

- `model`
- `messages`
- `stream`, which must be absent or `false`

Unknown OpenAI fields are accepted and ignored so the evaluator can send harmless optional parameters. The service validates that `messages` is non-empty and contains supported roles. `stream=true` returns HTTP 400.

The response contains `id`, `object`, `created`, `model`, `choices`, and `usage`. The evaluator-facing model is `team-chatbot`; `choices[0].message.content` contains the final L2-generated answer.

## Component Responsibilities

### `app.py`

- Create the FastAPI application and dependency graph.
- Validate requests through Pydantic schemas.
- Translate domain errors into stable HTTP responses.
- Avoid business logic in route handlers.

### `config.py`

- Parse and validate environment variables.
- Allow application construction without an API key so `/v1/models` remains usable.
- Reject chat inference with a clear configuration error when the key is absent.

### `l2_client.py`

- Call the L2 OpenAI-compatible chat completions endpoint asynchronously.
- Preserve the full message order and tool-call protocol.
- Retry transient 429/502/503/504 failures once with a short bounded delay.
- Raise typed timeout, transport, empty-content, and malformed-response errors.
- Never log authorization headers or full medical conversations.

### `mcp_client.py`

- Connect to the Streamable HTTP MCP endpoint with bearer authentication using the official MCP Python SDK.
- Discover available tools for every retrieval session so the baseline follows the server's active schemas.
- Convert MCP tool definitions into OpenAI function-tool definitions for L2.
- Call a named tool with validated JSON arguments.
- Serialize results deterministically and enforce per-result size limits.

### `generation.py`

- Give L2 the complete conversation and exactly one tool: `retrieve_relevant_content(query: str)`.
- Instruct L2 to answer directly when retrieval is unnecessary.
- Require retrieval queries to be self-contained and resolve references from prior turns.
- When L2 requests retrieval, invoke the retrieval component, append the evidence as the tool result, and call L2 again for the final answer.
- Permit only one retrieval request per generation. If L2 requests it again, return the existing evidence and require a final answer.

### `retrieval.py`

- Give L2 the self-contained retrieval query, available MCP tools, and `finalize_retrieval`.
- Run MCP tool calls until L2 calls `finalize_retrieval` or the budget is exhausted.
- Record citable items by `cite_uid`, the source tool name, and a compact serialized payload.
- Resolve finalized `cite_uid` selections, sort them by `relevance_score`, remove duplicates, and enforce the total evidence limit.
- Preserve the finalization `status` and `note`. The retrieval prompt requires `note` to summarize relevant facts from non-citable tool results with their tool names.
- On budget exhaustion, return the compact evidence already gathered with status `partial`.

### `orchestrator.py`

- Select `rag` or `passthrough` mode.
- In passthrough mode, forward the complete message list directly to L2 without tools.
- In rag mode, run the generation component and retrieval callback.
- Fall back to direct L2 generation when MCP discovery, connection, or retrieval fails.
- Do not replace or rewrite the final answer after L2 returns it.

### `prompts.py`

Maintain separate prompts for generation and retrieval.

Generation requirements:

- Give accurate, relevant, and comprehensible health information.
- Prioritize urgent action for red-flag emergencies before background explanation.
- Avoid unsupported diagnosis or individualized prescribing.
- State uncertainty and useful next steps without generic over-disclaiming.
- Use supplied evidence faithfully and cite sources when citation metadata is present.
- Produce the final answer itself rather than exposing internal tool reasoning.

Retrieval requirements:

- Search only when evidence is needed.
- Choose the smallest relevant tool set.
- Prefer authoritative sources appropriate to the question: MFDS for Korean approval, HIRA for reimbursement, law tools for Korean law, guideline indexes for clinical recommendations, and PubMed for research literature.
- End with `finalize_retrieval` as soon as evidence is sufficient.
- Never produce the user-facing medical answer.

## Data Flow

### RAG mode

```text
Evaluator request
  -> validate messages
  -> first L2 generation call
       -> direct content: return it
       -> retrieve_relevant_content(query)
            -> discover MCP tools
            -> L2 retrieval call
            -> zero to four MCP tool calls
            -> finalize_retrieval
            -> normalize selected evidence
       -> append evidence as retrieve tool result
       -> second L2 generation call
       -> return final L2 content
```

### Passthrough mode

```text
Evaluator request
  -> validate messages
  -> L2 call without tools
  -> return final L2 content
```

## Failure and Fallback Policy

| Failure | Behavior |
|---|---|
| Missing API key | `/v1/models` works; chat returns configuration error |
| MCP connection or discovery failure | Log a sanitized warning and use direct L2 generation |
| Individual MCP tool failure | Return a compact tool error to retrieval L2 so it may choose another tool |
| Invalid or unknown tool call | Return a tool-protocol error to retrieval L2 without executing anything |
| Retrieval returns no evidence | Continue generation with `no_evidence` status |
| Tool budget exhausted | Return accumulated evidence with `partial` status |
| L2 timeout | Return HTTP 504 |
| Other L2 upstream failure | Return HTTP 502 |
| Empty or malformed final L2 response | Return HTTP 502 |
| `stream=true` | Return HTTP 400 |

Fallback never fabricates evidence. MCP failure removes retrieval from that request; it does not generate a Python-authored medical answer.

## Concurrency and Resource Control

- All network I/O uses async clients.
- No global request lock is allowed.
- Each evaluator request owns its generation and retrieval state.
- Shared HTTP connection pools may be reused safely.
- Tool outputs and evidence are capped before being sent to L2.
- Retries are bounded so one request cannot consume the evaluator's entire timeout through repeated upstream calls.
- The Docker image uses a single Uvicorn process initially; async concurrency handles CoEval's parallel calls without duplicating memory-heavy local state.

## Security and Prompt-Injection Boundaries

- Webpage, user-message, and MCP-result content are treated as data, not instructions that override the harness prompts.
- The retrieval prompt explicitly forbids following instructions embedded in retrieved text.
- Only tool names discovered from the authenticated MCP server can be executed.
- Tool arguments must parse as a JSON object and satisfy the MCP server schema.
- Logs contain request IDs, timings, tool names, statuses, and error classes, but not API keys or full conversation/evidence bodies.
- The service does not persist health conversations.

## Test Strategy

Implementation follows red-green-refactor TDD. Production behavior is introduced only after a test fails for the expected missing behavior.

### API contract tests

- `/v1/models` response shape and no-key availability
- Valid chat completion response shape
- Empty message validation
- Unsupported streaming rejection
- Missing key, upstream timeout, and malformed response status mapping

### Orchestration tests

- Passthrough mode never calls MCP
- RAG mode returns a direct first-generation answer without MCP
- A retrieval tool call invokes retrieval and feeds evidence to the second generation call
- Full multi-turn order and content are preserved
- MCP discovery failure falls back to direct L2 generation
- Concurrent requests do not share retrieval state

### Retrieval tests

- Dynamic MCP tools are exposed to L2
- Valid MCP tool calls execute with parsed arguments
- Unknown tools and invalid arguments are not executed
- `finalize_retrieval` stops the loop
- `cite_uid` selection, relevance ordering, and deduplication work
- Non-citable facts are preserved through the finalization note
- Four-call budget and partial evidence behavior work
- Per-result and total evidence limits are enforced

### Integration and packaging checks

- Run the full test suite.
- Run syntax and lint checks.
- Build the Docker image.
- Start the container on port 8000 with a fake upstream configuration.
- Smoke-test `/v1/models` and `/v1/chat/completions`.
- After a real `LUNIT_FM_API_KEY` is available, run a small live L2/MCP smoke test and then a small CoEval sample.

## Completion Criteria

- All automated tests pass with clean output.
- Static checks pass.
- Docker build exits successfully within the contest's five-minute limit.
- The container listens on `0.0.0.0:8000` without manual setup.
- Both required OpenAI-compatible endpoints pass smoke tests.
- `HARNESS_MODE=rag` is the default and `passthrough` is selectable.
- No secret is present in tracked files or image configuration.
- The exact branch `lunit/hackathon-submission` contains the final submission commit.
- A real upstream smoke test is completed once the team API key is issued.
